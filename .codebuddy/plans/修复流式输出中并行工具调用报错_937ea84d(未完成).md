## 用户需求

habit-agent 项目（Spring Boot 4 + Spring AI 2.0.0，接入通义千问 qwen-plus）在流式对话接口运行时抛出 `java.lang.IllegalArgumentException: no more than one tool call per message currently supported`，导致流式输出不可用。用户要求：阅读项目现状，结合官方资料给出 Spring AI 2.0 流式输出的合理适配运行方式；凡是需要人工手动配置的部分，明确告知由用户自主修改。

## 产品概述

修正 Spring AI 2.0 流式工具调用在通义千问（OpenAI 兼容）模型下的并行工具调用不兼容问题，使 `/api/chat/stream` SSE 接口可稳定返回内容并正常执行业务工具。

## 核心功能

- 从源头关闭模型并行工具调用（parallel tool calls），避免一条 assistant 消息出现多个 tool call 触发 `ChunkMerger` 断言失败。
- 在 ChatClient 全局与 `stream()` 调用处双重设置 `parallelToolCalls=false` 作为兜底。
- 增强流式 error 回调日志，输出完整异常堆栈便于排障。
- 明确告知用户在 `application.yml` 的 `spring.ai.openai.chat.options` 下可手动补充 `parallel-tool-calls: false` 作为 YAML 层双保险（可选）。

## 技术栈选择

- 后端：Spring Boot 4.1.0 + Spring AI 2.0.0（spring-ai-starter-model-openai），接入通义千问 DashScope OpenAI 兼容端点。
- 模型：qwen-plus（对话）、text-embedding-v3（嵌入）。
- 流式：ChatClient `.stream().content()` + SSE（`SseEmitter`）。
- 工具：MethodToolCallbackProvider 注册 4 个 @Tool 业务工具类。

## 实现方案

### 根因

Spring AI 2.0.0 的 `OpenAiChatModel$ChunkMerger.mergeDeltas` 对合并后的 assistant 消息断言 `toolCalls <= 1`（`Assert.isTrue`）。通义千问 qwen-plus 默认启用 `parallel_tool_calls`，当用户意图复杂时一次返回多个并行工具调用，流式 chunk 合并后即触发 `IllegalArgumentException`。`ChatServiceImpl.stream()` 走 `.stream().content()`，且 `ChatClientConfig` 未关闭并行调用，故必现。

### 关键决策

1. **关闭并行工具调用（主修复）**：Spring AI 2.0.0 的 `OpenAiChatOptions` 提供 `parallelToolCalls(@Nullable Boolean)` 字段（等价 OpenAI `parallel_tool_calls`）。在 `ChatClient.Builder` 上设置 `defaultOptions(OpenAiChatOptions.builder().parallelToolCalls(false).build())`，从模型侧源头避免多 tool call。理由：改动集中在配置层、零侵入业务、与现有 `ChatClient.Builder` 自动读取 options 的约定一致。
2. **调用处兜底（次修复）**：在 `ChatServiceImpl.stream()` 的 `prompt().options(OpenAiChatOptions.builder().parallelToolCalls(false).build())` 再设一次，防止全局配置被局部覆盖而失效。该 options 会被合并进请求参数。
3. **YAML 双保险（用户手动，可选）**：`application.yml` 的 `spring.ai.openai.chat.options` 增加 `parallel-tool-calls: false`。该键会被 `ChatClient.Builder` 自动读取，与代码层二选一即可；作为人工配置项明确告知用户。
4. **日志增强（建议）**：`ChatController` SSE `error` 回调当前仅发 generic error，无堆栈。改为 `log.error("流式对话异常", error)` 输出完整堆栈，便于后续排障。

### 性能与可靠性

- 关闭并行工具调用对延迟影响极小（仅少一个请求级布尔参数）；工具执行仍按 Spring AI 内置 `internalToolExecutionEnabled=true` 的递归循环串行执行，功能不退化。
- `parallelToolCalls=false` 仅降低并行概率，极端情况下模型仍可能返回多个调用；若后续复现，可将 `stream()` 在检测到工具轮次时退化为 `.call()` 非流式（本计划不实现，作为预案告知用户）。

## 实现要点

- 复用现有 `ChatClient.Builder` 自动读取 options 的模式，不引入新架构。
- 修改 `ChatClientConfig` 仅追加 `.defaultOptions(...)`，保持既有 `defaultSystem/defaultAdvisors/defaultTools` 不变。
- `ChatServiceImpl.stream()` 使用 `org.springframework.ai.openai.OpenAiChatOptions` 显式覆盖 options，避免 N+1 或重复构建。
- `ChatController` error 回调用 `log.error(..., error)` 保留异常对象，不 dump 大 payload。

## 架构设计

改动维持现有分层（Controller → Service → ChatClient/Model），无新组件。数据流：HTTP SSE → ChatController → ChatService.stream() → ChatClient.prompt().options(parallelToolCalls=false).stream() → OpenAiChatModel → DashScope（parallel_tool_calls=false）→ 合并 chunk（单 tool call）→ SSE chunk 下发。
