## 用户需求

应用运行时创建自定义目标报错：`DataIntegrityViolationException: Duplicate entry '1-CUSTOM' for key 'habit_goal.uk_user_type'`，返回 500 系统异常。需要修复该 bug，使自定义目标能够正常添加（不同 customName 可共存多个，相同 customName 应返回友好的业务错误而非 500）。

## 问题根因

- 实体 `HabitGoal` 上定义了数据库唯一约束 `uk_user_type(user_id, goal_type)`。
- `GoalService.saveGoal` 仅对"非 CUSTOM"类型做了业务判重，CUSTOM 类型直接 `save`，与"自定义目标允许多个、通过 customName 区分"的业务语义冲突。
- 同一用户第 2 条 CUSTOM 目标插入时违反 `uk_user_type` 唯一约束；该异常未被 `GlobalExceptionHandler` 专门捕获，落入兜底 `Exception` 处理器，打印"系统异常"并返回 500。

## 核心修复点

- 移除 DB 层无法表达条件语义的唯一约束，改由业务层全量判重保证"内置类型唯一、CUSTOM 按 customName 唯一"。
- 为 `DataIntegrityViolationException` 增加兜底处理，避免任何遗漏的数据库约束再次暴露为 500。
- 清理数据库中已存在的旧唯一索引（Hibernate `ddl-auto: update` 不会自动删除）。

## 技术栈

- Spring Boot 4.1.0 + Spring Data JPA + Hibernate 7 + MySQL
- 现有全局异常处理：`@RestControllerAdvice`（GlobalExceptionHandler）
- 错误码常量：`AgentConstants.CODE_DUPLICATE_GOAL=40901`、`CODE_DB_ERROR=50002`

## 实现方案

### 策略

采用"业务层全量判重 + 移除 DB 唯一约束 + 异常兜底"三步修复。单靠 `@Table(uniqueConstraints)` 无法表达"内置类型唯一、CUSTOM 可多个"的条件语义（MySQL 多列唯一索引中 NULL 不判等，会把内置类型的 null `custom_name` 视为不同行，反而无法限制内置类型重复），因此唯一约束必须移除，重复校验完全交给业务层，既消除报错又精确匹配业务规则。

### 关键技术决策

1. **移除 `uk_user_type` 数据库唯一约束**：`HabitGoal.java` 的 `@Table` 删除 `uniqueConstraints`，仅保留非唯一的 `idx_user_active` 索引。内置类型唯一性、CUSTOM 按 customName 唯一性改由代码保证，无表结构歧义。
2. **完善 `GoalService.saveGoal` 判重逻辑**：内置类型（非 CUSTOM）按 `goalType` 判重；CUSTOM 类型按 `(goalType, customName)` 判重（customName 为空时按目标类型判重）。重复时抛 `BusinessException(CODE_DUPLICATE_GOAL, "该目标已存在")`，由现有 `GlobalExceptionHandler` 返回统一 `Result.error(40901,...)`，不再 500。
3. **`GlobalExceptionHandler` 新增 `DataIntegrityViolationException` 处理器**：作为兜底，将任何数据库完整性异常（含其他遗漏约束）转换为 `Result.error(CODE_DB_ERROR, "数据冲突，请检查是否重复添加")`，避免再次暴露 500 系统异常。
4. **清理旧索引**：因 `ddl-auto: update` 不会自动 drop 旧 `uk_user_type`，需在 MySQL 手动执行 `ALTER TABLE habit_goal DROP INDEX uk_user_type;`。该 SQL 在计划中给出说明，不自动执行，需用户确认数据库环境后手动运行。

### 性能与可靠性

- 判重基于已查出的 `findByUserId` 列表做内存流式过滤，单用户目标数据量极小（演示场景），无 N+1 或额外查询开销。
- 异常兜底处理器仅在出错时触发，正常路径零额外开销。
- 业务层判重与 DB 约束移除一致，避免并发插入极小概率的竞态（演示单用户场景可接受；如需强一致可在 DB 层加函数索引，但超出本次范围）。

## 实现注意事项

- 不改 Controller、不改除 `saveGoal` 外的 Service 逻辑、不动实体其他字段。
- `customName` 判重需考虑 null/空串归一（trim 后为空视为未命名自定义目标，按类型判重）。
- 修改完成后执行 `mvn compile` 验证编译；并按约定 git 提交并推送远程仓库。

## 架构设计

当前分层架构 Controller → Service → Repository(JPA) 不变。本次仅在 `HabitGoal` 实体（约束定义）、`GoalService`（判重逻辑）、`GlobalExceptionHandler`（异常分支）三处改动，属局部修复，不引入新模块或新依赖。

## 关键代码结构

`GoalService.saveGoal` 判重逻辑（目标片段，仅示意核心）：

```java
// 内置类型：同一类型只允许一个
// 自定义类型：按 (goalType, customName) 判重
boolean duplicate = habitGoalRepository.findByUserId(goal.getUserId()).stream()
    .anyMatch(g -> g.getGoalType() == goal.getGoalType()
        && java.util.Objects.equals(normalize(g.getCustomName()), normalize(goal.getCustomName())));
if (duplicate) {
    throw new BusinessException(AgentConstants.CODE_DUPLICATE_GOAL, "该目标已存在");
}
```

`GlobalExceptionHandler` 新增：

```java
@ExceptionHandler(org.springframework.dao.DataIntegrityViolationException.class)
public ResponseEntity<Result<Void>> handleDataIntegrity(DataIntegrityViolationException ex) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
        .body(Result.error(AgentConstants.CODE_DB_ERROR, "数据冲突，请检查是否重复添加"));
}
```
